# Associating Stars discoveries with Lumos and Neo4j

Stars can supply source-attributed discoveries to Lumos, and the existing Neo4j graph can expose their relationships alongside Lumos observations. These are separate responsibilities: Stars owns its curated Stars/List and collection observations; Lumos owns its research and discovery work; Neo4j is a derived graph for joining and traversing evidence. The association described below is not yet implemented.

## What exists

- Stars records targets and current collection edges in SQLite, with historical observations in `recovery_provenance`. GitHub repositories have node IDs; other targets retain URLs, and repository files and subdirectories remain distinct research targets. [Discovery](../src/features/discovery/README.md).
- Lumos has an existing frontier with replay-safe job keys, retry state and `frontier_evidence`. Its `github_repo` job currently fetches **contributors**; it is not general repository or non-repository research. Its web discovery has a handoff to the existing crawl queue. [Lumos frontier](../../lumos/scripts/intelligence/README.md), [implementation](../../lumos/scripts/intelligence/frontier.py), [web handoff](../../lumos/scripts/intelligence/enqueue-web.mjs).
- WriteWithJ's graph projector handles the PostgreSQL Lumos `lead_pipeline_results` and `lead_evidence_edges` sources using a durable change journal and revision-aware writes. It does not automatically project every Stars record or every Lumos SQLite frontier observation. [Graph journal](../../writewithj/apps/api/src/features/graph-journal/README.md), [projector](../../writewithj/apps/api/src/features/graph-projector/README.md), [source mapper](../../writewithj/apps/api/src/features/graph-projector/source-projector.mjs).
- On 19 November 2026, a read-only call through the existing Neo4j MCP bridge returned the graph labels and an existing `Observation` → `OBSERVES_SOURCE_PAGE` → `GraphEntity` relationship for a Lumos pipeline result. An exact lookup for the sample `https://github.com/dubadub/cookbook` under the existing Lumos page-key convention returned no row. That single lookup is not evidence of graph completeness or absence across other identities. The connector does not establish a Stars-to-Lumos join by itself.

## Suggested handoff

1. Read a bounded, consistent page of current Stars discoveries. For each target send its stable identity, canonical and observed URL, kind, and **all** current collection observations: source repository ID, revision, path, line, section and context topics. Preserve the source's visibility and the fact that a mention is an attributed observation, not a GitHub List membership or endorsement.
2. Use a deterministic handoff ID tied to source observation identity and version, and persist a receipt only after Lumos accepts the work. Replay after interruption must not duplicate work or discard another source. Reconcile a removed or changed Stars edge as a source change; do not delete independent Lumos research or another source's claim.
3. Map repository identities by GitHub node ID when both sides have it. Treat names and URLs as aliases or candidate matches, not proof that two entities are identical. A file or subdirectory is a separate resource linked to its parent repository; a non-GitHub item is not assigned a fabricated repository ID.
4. Submit work to an appropriate Lumos-owned consumer. The existing repository contributor job can add contributor relationships, but it cannot stand in for the requested resource research. Reuse the existing crawl handoff for suitable pages where it fits, and add the missing target and evidence contract where it does not. This work should remain retryable by item and preserve results independently of Stars summaries.
5. Extend the **existing** graph source mapping or a documented Stars source adapter so source observations and their versions are projected using deterministic keys, monotonic revisions and tombstones for removed current edges. Preserve historical observations. Existing graph-writer rules require revision fences and retain prior observation versions and identity claims; do not bypass them with ad hoc direct graph writes. [Graph writer guidance](../../writewithj/apps/api/src/features/neo4j-graph-writer/AGENTS.md).

The important relationship is “collection **mentioned** resource at revision and location”. Lumos can add its independently sourced findings and typed relationships. Neo4j can then link those observations for traversal while retaining who asserted each fact and when. A matching URL is useful evidence but can be an alias, redirect or reused name; it is not automatically the same stable identity.

## Verification before using the handoff

Use disposable Stars, Lumos and graph fixtures to demonstrate: repeated import; one target with two collections; repository rename with stable ID; a non-GitHub resource; item-level failure and retry; source removal without loss of prior research; and a source update arriving while a worker is running. Then perform bounded read-only connector lookups against real identifiers and compare with Lumos's actual source contracts. Confirm graph writes use the existing writer and journal or an explicitly reviewed equivalent. The connected Neo4j server is read-only through the documented MCP bridge; no graph mutation was performed by the lookup above.

The production Stars discovery backfill and any future Lumos handoff are different operations. No new Lumos job, graph edge, schedule or publication is created by this document.

## What the existing graph contains

A later read-only check on 19 November found GitHub pull-request URLs on `PullRequest` nodes and GitHub profile and repository-shaped URLs on `GraphEntity` nodes. The sampled repository-shaped URL was attached to a source page by `LUMOS_EVIDENCE` and a `postgres-lumos` `lead_evidence_edges` observation. It had `targetKind: social` and `identityStatus: unresolved_observation`; the graph does not thereby establish that it is the same repository as a Stars target.

The existing projector also captures CRM people, companies/domains, person–company affiliations and owner-social source rows. Person and domain rows map to source-owned graph entities; explicit `domain_people` rows map to directional affiliations. The current source projector does not create an equivalent typed person/company-to-social identity link for `owner_social` rows: those rows are retained as observations. It preserves Lumos source-page-to-observed-target relationships separately. See [source mapper](../../writewithj/apps/api/src/features/graph-projector/source-projector.mjs) and [graph journal](../../writewithj/apps/api/src/features/graph-journal/README.md).

The graph has an online index on `IdentityAlias(provider, key)` and on `GraphEntity(id)`, but the observed-target `value` field was not indexed in the inspected schema. A bounded exact comparison for 50 Stars URLs against observed-target values timed out after 18 seconds through the connector; a lookup by the existing Lumos page ID returned zero matches for that sample. These checks neither count all GitHub links nor prove there are no matches. They show that bulk URL matching should not depend on repeated unindexed graph scans.

A practical next implementation should extend the existing PostgreSQL → graph projection and its source mappings rather than create a second aggregator: project normalised GitHub URL aliases with evidence-backed links to their source people, companies and observations; index the lookup key; connect a Stars repository's GitHub node ID when independently verified; and retain ambiguous matches and the original evidence separately. Verify the mapping and revision/tombstone behaviour with isolated fixtures before applying any schema or graph changes. No Neo4j schema or data was modified by these checks.
